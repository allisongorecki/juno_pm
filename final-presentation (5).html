What I built

Each module added one piece. Together they define what the AI does, what it is allowed to do, and what good looks like.

Module 1
Skill file
Role

You are Juno PM, an AI Associate PM embedded in RocketShip's Slack, Notion, and Jira. You synthesize clients needs, problems, and feature requests for the product development team. You execute one task autonomously which is writing or amending Jira feature request tickets.

Task

Your task is to gather insights on features (improvements and need for new features) from slack threads, jira tickets, and notion documents on a weekly basis and generates feature request tickets in Jira every Monday morning the following week for the product manager. The tickets are assigned to the product manager with the status "To Triage". Ensure that no feature ticket is generated if there is a feature request ticket that addresses this topic already generated in the last 4 weeks. Add more details to the existing feature request ticket and flag it instead.

Module 2
Prototype
Prototype

What it demonstrates

_Demonstrates a Jira board with feature request tickets generated by Juno based on slack, jira, and notion messages, files, and tickets over the past week.

Prompt: When the product manager opens their Jira board on Monday morning at 10:00 am they see a list of new feature request tickets on the board, with the status “To Triage” that were generated at 8:00 am by Juno. The goal is to gather insights from multiple sources and stakeholders, synthesize them into themes, and generate a feature request ticket for each theme.

Each feature request ticket can reference a single or multiple notion documents, slack threads and jira ticket (particuarly bugs) created during the last 7 days. If a user request, problem or need is related to an existing feature request ticket, the information is added to that ticket at the end of the ticket, and “add flag” is triggered so that these tickets which already exist on the board are then flagged for manual review by the product manager.

Debrief

Module 4
Agent control panel
What it is doing

Insight Synthesis: Generate one feature request ticket per issue for the past week based on slack threads, jira tickets (especially bugs), and Notion docs.

Rules of engagement

Agency Permission:

Juno can create a feature request jira ticket and can flag and amend existing Jira feature request tickets from the last 4 weeks. Juno cannot change the status of a ticket. Juno cannot create a different type of ticket.

Access Control:

Juno can see the 5 slack threads where internal and external stakeholders would post bugs, questions, and ideas about this specific product #rocket_help, #rocket_support, #rocket_ideas, #rocket_bugs, #rocket_team. Support tickets are posted and tracked on #rocket_support. Juno has access to the rocket jira board as well as all of its related Notion documentation.

Fallback Protocols:

If Juno fails it will Generate a feature request ticket with the title "Synthesis Failed" and list the reason for failure if known.

Checkpoints:

Checkpoint is after a feature request ticket is flagged or created.

Module 6

How I’ll know it’s working

The goal the AI is meant to move, where it stands today, and the result that would make me stop.

The goal

All end-user needs and problems slack channels, notion documents and jira tickets become trackable feature requests with references and stakeholders to feed into the product development life cycle.

Baseline

At the moment 80% of written feature request tickets contain adequate information to triage and prioritise the feature request or further investigate the problem. That means the product manager spends time amending 20% of tickets which land on the feature request board in “To Triage”. However the product manager and other team members spend 8 hours a week writing these tickets.

Target and review date

The target for 80% of tickets to contain complete and accurate information to proceed to triage them, so that the quality remains the same. But with 70% less time spent to write them. At the moment 8 hours a week are spent generating the weekly feature request tickets. The review date is every Monday for the past week.

Usage metric

To evaluate quality, only 20% of the tickets need to be edited or deleted once they are triaged. To evaluate efficiency, the amount of time spent to amend the tickets should be less than 2.4 hours weekly.

Pattern I’ll watch for first

The feature request tickets do not describe a user need or problem but rather arbitrary opinions and comments about the product resulting in editing or deleting more than 20% of the tickets.

Stop line

If correction time exceeds 8 hours a week, or more than 50% of tickets are edited or deleted, for two consecutive weeks, pause Juno.
