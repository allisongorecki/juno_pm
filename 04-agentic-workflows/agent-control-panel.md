# Agent Control Panel · Juno

_Module 4 deliverable. Generated by `M4 - Agent Control Panel.html`. Paste over `04-agentic-workflows/agent-control-panel.md`._

## What Juno Is Doing

Insight Synthesis: Generate one feature request ticket per issue for the past week based on slack threads, jira tickets (especially bugs), support tickets and Notion docs.

## Four Levers

**Stop Conditions** (Loop):

The agent is semi-autonomous. The agent is done once it has synthesized data from the past week, verified if it should add this to an existing feature request ticket less than 4 weeks old or created a new feature request Jira ticket. It can loop only twice in case it missed some references that provide the proof that the feature is addressing an end-user need or problem.  If the agent runs for longer than 12 hours it should timeout.

**Structured Tool Outputs** (Tools):

Tool	Works → returns	Fails → returns	Silent failure Juno checks for
read_slack (channels, since, until)	status: ok | empty, threads_returned, channels_searched vs channels_requested, the window it actually applied, and per thread id, permalink, message_count	status: error, error_code (auth_expired, rate_limited, channel_not_found, timeout), channels_failed[], retryable: true/false	channels_searched < channels_requested means partial. An echoed window that doesn’t match the requested week means a bad filter. A count far below last week’s suggests a broken query.
read_jira (JQL, since)	status, issues_returned, total_matching, truncated: true/false, and per issue key, type, priority, url	status: error, error_code (invalid_jql, auth, project_permission_denied)	issues_returned < total_matching means it must paginate before continuing. Zero bugs in a week is worth a flag.
read_support (since, until)	status, tickets_returned, oldest_ts / newest_ts, and per ticket id, customer_id, url	status: error, error_code, retryable	If newest_ts is days before the window’s end, the sync is stale even though the call “worked.”
read_notion (query, since)	status, pages_returned, pages_skipped_no_access	status: error, error_code	pages_skipped_no_access > 0 means the integration isn’t shared with those pages. That is the classic Notion silent gap.
find_existing_ticket (issue summary)	status: match | no_match, match_count, best_match_key, similarity (0–1), threshold	status: error (store unavailable or timeout)	error must never be read as no_match. If memory fails, Juno doesn’t create, or it will duplicate.
create_feature_ticket	status: created, ticket_key, url, and a read-back of column, assignee, impact / effort / risk scores, source_links_count	status: error, error_code (validation_failed + fields[], permission_denied, duplicate_detected)	The read-back must show column == "To Triage" and assignee == PM. source_links_count must be at least 1 and equal the number of sources Juno cited.
amend_feature_ticket (key, changes)	status: updated | unchanged, fields_changed[], previous_values, ticket_age_days	status: error, error_code (out_of_window (>28 days), not_found, not_juno_ticket, left_triage, version_conflict)	left_triage means the PM has picked it up, so don’t touch it. version_conflict means a human edited it since Juno read it. unchanged with a non-empty change request means the edit didn’t land.

Three rules make these contracts actually catch things:

Error never counts as empty. Juno only treats a source as “nothing this week” when it gets status: empty together with full coverage (all channels searched, nothing truncated).
A failed lookup blocks writes. If find_existing_ticket errors, Juno skips creating that ticket and logs it. It does not guess.
The run reports its own coverage. At the end of each loop, Juno emits sources_ok: 3/4, tickets_created, tickets_amended, and tickets_failed. If any source was partial, that gets noted on the tickets it produced, so the PM knows the prioritisation was based on incomplete input.

**Confidence Thresholds** (Verification):

Because a PM will triage all the tickets that it generates manually, Juno can execute it full workflow regardless of level of confidence (low, medium, and high is acceptable).

**North Star** (Context):

Insight Synthesis: Generate one feature request ticket per issue for the past week based on slack threads, jira tickets (especially bugs), support tickets and Notion docs. Be sure to include the reference to the source in the ticket. Do not invent information or sources.

## Rules of Engagement

**Agency Permission:**

Juno can create a feature request jira ticket and can flag and amend existing Jira feature request tickets from the last 4 weeks. Juno cannot change the status of a ticket. Juno cannot create a different type of ticket.

**Access Control:**

Juno can see the 5 slack threads where internal and external stakeholders would post bugs, questions, and ideas about this specific product #rocket_help, #rocket_support, #rocket_ideas, #rocket_bugs, #rocket_team. Support tickets are posted and tracked on #rocket_support. Juno has access to the rocket jira board as well as all of its related Notion documentation.

**Fallback Protocols:**

If Juno fails it will Generate a feature request ticket with the title "Synthesis Failed" and list the reason for failure if known.

**Checkpoints:**

Its a very simple agent, so there's not fixed point needed in this workflow.
