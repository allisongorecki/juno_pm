## What Juno Is Doing

Insight Synthesis: Generate one feature request ticket per issue for the past week based on slack threads, jira tickets (especially bugs), support tickets and Notion docs.

## Four Levers

**Stop Conditions** (Loop):

The agent is semi-autonomous. The agent is done once it has synthesized data from the past week, verified if it should add this to an existing feature request ticket less than 4 weeks old or created a new feature request Jira ticket. It can loop only twice in case it missed some references that provide the proof that the feature is addressing an end-user need or problem.  If the agent runs for longer than 12 hours it should timeout.

**Structured Tool Outputs** (Tools):

Your Tools section names two things Juno does (generate tickets, prioritise them). Those are Juno’s own reasoning, not tools. The tools sit underneath: reads from four sources, a memory lookup, and writes to Jira. Below is each one with what it returns when it works and when it fails.

One rule across all of them: every tool returns a status of ok, empty, partial or error. Silent failures mostly happen when a failed read looks like an empty one. “No Slack threads this week” and “Slack auth expired” must never come back as the same thing.

1. search_slack_threads(channels, since, until)

Works: status: ok, threads: 42, channels_scanned: 6/6, window: 2026-11-01→11-07, has_more: false
Fails: status: error | partial, error_code: auth_revoked | rate_limited | channel_not_found, channels_scanned: 4/6
Juno checks: whether channels_scanned equals the number requested, whether has_more is false, and whether the window matches the past week. Zero threads across six channels in a week counts as a warning, not a clean result.

2. search_jira_issues(jql)

Works: status: ok, total: 31, returned: 31, bugs: 12
Fails: status: error, error_code: jql_invalid | forbidden, or returned: 50, total: 87 (truncated)
Juno checks: whether returned equals total. If not, the result is partial and Juno pages again before scoring anything.

3. search_support_tickets(since, until)

Works: status: ok, tickets: 18, window: …
Fails: status: error, error_code: …, or tickets: 0 when last week’s count was over 10
Juno checks: the window, plus a sanity bound against the previous run’s count, which you already keep in memory.

4. fetch_notion_docs(query | page_ids)

Works: status: ok, pages_found: 9, pages_read: 9
Fails: status: partial, pages_found: 9, pages_read: 6, pages_forbidden: 3
Juno checks: whether pages_read equals pages_found. Forbidden pages get listed in the run summary, not dropped silently.

5. lookup_previous_tickets(summary) (memory, dedupe)

Works: status: ok, matches: [{key: PROD-412, similarity: 0.87}] or status: ok, matches: []
Fails: status: error, error_code: index_unavailable
Juno checks: a match at or above a threshold you set (say 0.80) means update, not create. Below the threshold means create. An error means hold the ticket, never create it. This is the most dangerous silent failure in your harness, because a failed lookup reads exactly like “no duplicates” and you end up with double tickets.

6. score_ticket output (Juno’s own judgment, but forced into a schema)

Works: impact: 4, effort: 2, risk: 3, priority: P1, evidence_count: 5
Fails: a dimension missing, a value outside 1–5, or evidence_count: 0
Juno checks: schema validation. A ticket scored on zero linked sources gets rejected and re-scored, or flagged insufficient_evidence.

7. create_jira_ticket(fields)

Works: status: ok, key: PROD-482, column: Triage, assignee: <PM id>, links_attached: 4
Fails: status: error, error_code: permission_denied | field_invalid, or a success where column ≠ Triage
Juno checks: three things. column == Triage and the correct assignee together enforce your Permissions section. links_attached must equal the number of sources the ticket cites, which enforces your Verification section.

8. update_jira_ticket(key, fields) (reprioritise or refine)

Works: status: ok, key: PROD-412, fields_changed: [priority], column: Triage
Fails: status: error, error_code: not_found | conflict, or fields_changed: []
Juno checks: whether fields_changed matches what it meant to change, and whether the ticket is still in Triage.

9. check_links(urls) (your Verification step)

Works: links_total: 4, links_resolving: 4
Fails: links_resolving: 3, broken: [<url>]
Juno checks: whether links_resolving equals links_total before the ticket is written.

Run receipt. Since your loop runs twice, end each run with a single checkable summary:

sources_ok: 3/4, tickets_created: 5, tickets_updated: 2, held_for_dedupe_error: 1, rejected_low_evidence: 0

The PM reads that line first. Anything other than 4/4 and zero holds means the week’s set is incomplete.

**Confidence Thresholds** (Verification):

Because a PM will triage all the tickets that it generates manually, Juno can execute it full workflow regardless of level of confidence (low, medium, and high is acceptable).

**North Star** (Context):

Insight Synthesis: Generate one feature request ticket per issue for the past week based on slack threads, jira tickets (especially bugs), support tickets and Notion docs. Be sure to include the reference to the source in the ticket. Do not invent information or sources.

## Rules of Engagement

**Agency Permission:**

Juno can create a feature request jira ticket and can flag and amend existing Jira feature request tickets from the last 4 weeks. Juno cannot change the status of a ticket. Juno cannot create a different type of ticket.

**Access Control:**

Juno can see the 5 slack threads where internal and external stakeholders would post bugs, questions, and ideas about this specific product #rocket_help, #rocket_support, #rocket_ideas, #rocket_bugs, #rocket_team. Support tickets are posted and tracked on #rocket_support. Juno has access to the rocket jira board as well as all of its related Notion documentation.

**Fallback Protocols:**

If Juno fails it will Generate a feature request ticket with the title "Synthesis Failed" and list the reason for failure if known.

**Checkpoints:**

Its a very simple agent, so there's not fixed point needed in this workflow.
