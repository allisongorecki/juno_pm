## Problem & user

RocketShip PMs need this handled: Generate a feature request ticket per issue for the past week based on slack threads, jira tickets (especially bugs), support tickets and Notion docs.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## The harness

| Surface | Specification |
|---|---|
| 01 Context | Slack threads, jira tickets, and Notion documents. |
| 02 Tools | It can generate feature request tickets. It can flag existing feature request tickets less than 30 days old if the topic is mentioned again… |
| 03 Loop | Twice. |
| 04 Memory | It remembers previously generated feature request tickets (last 30 days) so as to not generate duplicates. |
| 05 Permissions | read auto · draft auto · write auto · send blocked |
| 06 Verification | It adds the links to the slack threads, emails, or Jira tickets at the end of the ticket. |

## 01 Context · Data Requirements

**Required sources, and exclusions**

Slack threads, jira tickets, and Notion documents.

**How fresh must it be**

The loop should fail if one of the sources is unreachable.

## 02 Tools · System Capabilities

**The verb list**

It can generate feature request tickets. It can flag existing feature request tickets less than 30 days old if the topic is mentioned again in a one of the sources. It can synthesize messages into feature request themes based on user needs, problems, and feedback.

**Deliberate omissions**

The tool does not transform the feature request into a ticket ready for development. The feature request ticket highlights the problem and possible impact of finding a solution, but not the solution itself per say.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

Twice.

**Latency and cost target**

It should generate feature request tickets daily with a latency of 12 hours. The target is to reduce cost and not speed.

## 04 Memory · Data Requirements

**What persists, at what scope**

It remembers previously generated feature request tickets (last 30 days) so as to not generate duplicates. It can reprioritise a previous feature request ticket or refine it.

**Expiry and write rules**

It no longer refers to previously generated request tickets once they are older than 30 days.  A human always outranks with all corrections. If a human has manually reprioritised a ticket, do not reprioritise to previous value and rather add a flag to that ticket.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | auto |
| send | blocked |

**Justification**

No feature request tickets move beyond the "To Triage" column in Jira. The tickets are assigned to the product manager.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

It adds the links to the slack threads, emails, or Jira tickets at the end of the ticket.

**Failure behaviour**

If the check fails, write that the check failed where the link for the source would be so that the product manager can reject the ticket or manually look for the source.
